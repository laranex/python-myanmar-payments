# Changelog

All notable changes to `python-myanmar-payments` will be documented in this file.

## v4.0.0 - Unreleased

Initial release. The version number matches the other Laranex Myanmar payments packages (`php-myanmar-payments`, `laravel-myanmar-payments`, `go-myanmar-payments`, `node-myanmar-payments`), and the gateways, flows, validation, signing, status maps, results and errors are a port of them, sharing their test vectors.

### Added
- Gateways: KBZ Pay (`pwa`, `qr`, `app`, `status`), Wave Pay (`initiate`), AYA Payment Gateway (`services`, `initiate`, `status`, `verify_redirect`), Yoma MMQR (`initiate`, `renew_qr`, `status`, `forget_token`) and CyberSource Secure Acceptance (`initiate`); every gateway validates its payment data (`KbzPay.validate()` and so on) and verifies callbacks with `handle_callback`.
- A sync and an async client for every gateway that calls an API (`KbzPay` / `AsyncKbzPay`, `WavePay` / `AsyncWavePay`, `AyaPay` / `AsyncAyaPay`, `YomaMmqr` / `AsyncYomaMmqr`), sharing one implementation of signing, validation and response parsing. `CyberSource` makes no network calls and serves both.
- `httpx` is the only runtime dependency: pass your own `httpx.Client` / `httpx.AsyncClient` as `http_client` (it keeps its own timeout), or let the gateway create one and close it with `close()` / `aclose()` or a `with` / `async with` block. With the client it creates, `timeout_seconds` is one overall deadline per request (connecting, sending and reading the whole response), like the other SDKs; a request past it raises `ApiError("Could not reach <url>: timed out")`.
- Exact `Amount` type (`Amount.kyat()`, `Amount.parse()`, `Amount.of()`) kept as decimal text, so amounts never pass through a float; payment data also takes a whole `int`, decimal text or a `Decimal`, and rejects floats. Decimals are accepted only where the gateway documents them (KBZ Pay up to 2 places, CyberSource any); KBZ Pay, Wave Pay and AYA are MMK only.
- Typed payment data dataclasses (`KbzPayPaymentData`, `WavePayPaymentData` with `WavePayItem`, `AyaPayPaymentData`, `YomaMmqrPaymentData`, `CyberSourcePaymentData`) and a config class per gateway with `from_env()` (default `os.environ`), reading the same credential, setting and URL variables as the PHP, Laravel, Go and Node packages; a missing setting raises `ConfigurationError`. Gateways, `MyanmarPayments` and `AsyncMyanmarPayments` take config objects or mappings of their keyword arguments (other keys are ignored, like PHP's `fromArray`); the facades build every gateway lazily, also from the environment. Text settings also take integers (`200123` becomes `"200123"`); floats, booleans and blank text count as missing.
- Configuration: every setting of a gateway you use is required and has no default, except the HTTP timeout (`timeout_seconds`, `MYANMAR_PAYMENTS_HTTP_TIMEOUT`), which defaults to `DEFAULT_TIMEOUT_SECONDS` (30). That includes the URLs (`base_url`, `api_url`, `pwa_url`, `base_redirect_url`; the config classes' `PRODUCTION_*` constants name the production URLs), the time to live (KBZ Pay's `time_to_live_minutes`, 1 to 120; Wave Pay's `time_to_live_seconds`, greater than 0), Yoma MMQR's `webhook_secret` (checked on every callback's `X-Webhook-Secret`), Wave Pay's `merchant_name` and Yoma MMQR's `api_version`; CyberSource payments take `currency`, `locale` and `transaction_type`. A missing or blank setting raises the `ConfigurationError` naming it; a time setting that is not a whole number from 1 to 2147483647 raises `The <gateway> configuration [<key>] must be a whole number greater than 0.` Settings are checked in the same order as the other SDKs: credentials, URLs and other text settings, then the time to live, then the HTTP timeout.
- Wave Pay follows the Pay with Wave API spec v1.3: payments are a JSON post to `base_url`'s `/payment` (Content-Type and Accept `application/json`) with `amount` and `time_to_live_in_seconds` as JSON integers, `currency` `MMK` and `items` as a JSON string array, and the customer is sent to `base_redirect_url`'s `/authenticate` (UAT: `https://preprodpayments.wavemoney.io:8107` for both; production: `https://payments.wavemoney.io`). `WavePayPaymentData` takes optional `additional_field_3`, `additional_field_4` and `additional_field_5` (at most 50 each, sent only when non-empty) and enforces the spec's limits: `order_id` and `merchant_reference_id` at most 100, `callback_url`, `return_url` and `description` at most 255. Limits count UTF-8 bytes.
- Wave Pay callback statuses per the spec: `PAYMENT_CONFIRMED` is successful; `BILL_COLLECTION_FAILED`, `INSUFFICIENT_BALANCE` and `ACCOUNT_LOCKED` are failed; `SCHEDULER_TRANSACTION_TIMED_OUT` (and `TRANSACTION_TIMED_OUT`) is expired; `PAYMENT_REQUEST_CANCELLED` is canceled. Callbacks fall back to `merchantReferenceId` for the order id when `orderId` is missing, null or empty.
- Result classes: `RedirectPayment`, `FormPayment` (with `to_html()`), `QrPayment` (with `qr_image_data_uri()`) and `AppPayment` (with `to_dict()`); `PaymentCallback` (with a gateway-independent `PaymentStatus` and the `Acknowledgement` each gateway expects, in its `acknowledgement` attribute) and `PaymentStatusResult`.
- `CallbackRequest(body=..., headers=..., query=...)` takes the raw body bytes, headers and query string from Django, Flask, FastAPI or any other framework; `CallbackRequest.from_json()` replays a stored callback. JSON numbers in callbacks are read without a float conversion, so signatures and amounts keep the gateway's exact text, and `raw` (like `parsed_body()`, `input()` and error `raw`) holds every JSON number as its exact text, e.g. `"1000.50"`.
- Errors: `PaymentError` and its subclasses `InvalidPaymentDataError` (per-field `errors`), `ApiError` (`gateway_code`, `gateway_message`, `http_status`, `raw`, network errors chained as `__cause__`), `SignatureVerificationError` and `ConfigurationError`.
- An injectable `TokenCache` (or `AsyncTokenCache` for the async client) with a thread-safe in-memory default for Yoma's access token; concurrent calls share one token request.
- Callback verification is the same in every Laranex payments SDK, checked by shared vectors (`tests/fixtures/parity/vectors.json`): numbers sign as the exact text sent, booleans as `true` / `false`, and a nested value (object or list) in a signed field fails verification.
- `Amount.equals()` and `==` compare by value, ignoring leading zeros and trailing fractional zeros (`"01000"` equals `Amount.kyat(1000)`); text that is not plain digits never equals.
- CyberSource callbacks trust only the fields listed in `signed_field_names`: `decision`, `req_reference_number` and `signed_field_names` itself must be signed, and unsigned fields are left out of the result and `raw`.
- Callbacks are checked beyond the signature where a gateway's signed text could be re-split: AYA Pay rejects `:` in signed values other than `dateTime` (empty, or `YYYY-MM-DD HH:MM:SS`) and requires `merchOrderId`, `tranId`, `amount`, currency `104` and a two digit `statusCode` (orders reject `:` in `order_id`, `description` and `user_refs` with `The <field> field must not contain ":".`); CyberSource rejects empty, repeated or `=` holding signed names and unknown decisions; Wave Pay requires a decimal `amount` and IDs of letters, numbers, `_` and `-`. Undecodable data, nested values, a non-string signature field and a wrong signature fail with `<Gateway> <thing> <signature|hash|checksum> verification failed.`; a correctly signed callback that fails these checks fails with `Wave Pay callback is malformed.`, `AYA Pay <context> payload is malformed.` or `CyberSource callback is malformed.`, the same texts and order as the other SDKs. `FormPayment.to_html(nonce)` adds a Content Security Policy nonce to the inline script (an empty nonce adds none).
- AYA Pay reads a `payload` whose `+` signs became spaces in an unencoded return query string, with or without base64 padding; partial padding, other alphabets and payloads that are not UTF-8 are rejected.
- Yoma MMQR caches its token under `myanmar-payments.yoma-mmqr.token.<sha256 of base URL|client id>`, the same key as the PHP, Go and Node SDKs, so services in different languages can share one cache.
- Callback, return and cancel URLs only need to be valid absolute http or https URLs; there is no HTTPS-only rule (gateways may still require HTTPS in production). URLs are checked like PHP's `FILTER_VALIDATE_URL` in every SDK: printable ASCII only, `http://` or `https://` followed by a bracketed IP or a host name of letters, digits and inner `-` (labels up to 63, at most 253 in all, one trailing dot allowed) and a port from 0 to 65535.
- Blank checks and trimming (settings, environment variables, required fields, statuses and callback bodies) use only ASCII whitespace and NUL, like PHP's `trim()`: a no-break space or a byte order mark is a character. A negative whole-number amount is reported with the other errors as `The <field> field must not be negative.` (`items.<i>.amount` for a Wave Pay item). Yoma MMQR reads `expires_in` from its leading digits after ASCII whitespace (`"+28800"` falls back to an hour); CyberSource callbacks with empty `auth_amount` and `req_amount` have no `amount`.
- Fully typed (`py.typed`, `mypy --strict`).
- Agent skill in `skills/python-myanmar-payments` so coding agents use the package correctly; install it with `npx skills add laranex/python-myanmar-payments`.
- Requires Python 3.10 or higher.
- Wave Pay per-payment overrides: `WavePayPaymentData` takes optional `merchant_name` and `time_to_live_seconds`, which replace the configured `merchant_name` and `time_to_live_seconds` for that payment (`time_to_live_seconds` also in the request hash). The configured `merchant_name` stays required. A blank `merchant_name` fails validation with `The merchant_name field is required.`, a `time_to_live_seconds` that is not an `int` (booleans, floats and text included) with `The time_to_live_seconds field must be an integer.`, and one below 1 with `The time_to_live_seconds field must be greater than 0.` Wave Pay payment data is validated in the same order as the other SDKs, with the items and the amount last; without items and an `amount` the error is `The amount field is required.`
- `KBZ_PAY_TIME_TO_LIVE_IN_MINUTES` sets every KBZ Pay order's time to live (1 to 120); a payment's own `time_to_live_minutes` overrides it.
